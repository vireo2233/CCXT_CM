# 第 11 课：Bifu 错误怎样变成 CCXT 异常

| Bifu 情况 | CCXT 异常 | 调用方应该怎么做 |
|---|---|---|
| 标的不存在 | `BadSymbol` | 检查交易对，不要原样重试 |
| 价格、数量、精度或订单参数不合法 | `InvalidOrder` | 修正订单参数后再提交 |
| 余额或信用额度不足 | `InsufficientFunds` | 检查余额和冻结资金 |
| 签名或身份无效 | `AuthenticationError` | 检查当前环境的 Key、Secret 和签名 |
| 没有权限 | `PermissionDenied` | 检查 API Key 权限，不能靠重复请求解决 |
| 账户类型未开通（如普通账户调用 `SANDBOX_MARKET`） | `AccountNotEnabled` | 申请对应账户类型或更换正确的 Key |
| 订单不存在或不属于当前账户 | `OrderNotFound` | 使用原订单号核对，不泄露其他账户的订单是否存在 |
| 重复客户端订单号 | `DuplicateOrderId` | 用原客户端订单号查单，不要立刻换号重下 |
| 请求过多或资源额度耗尽 | `RateLimitExceeded` | 等待并按上层限速策略重试 |
| 服务不可用或缺少指数价格 | `ExchangeNotAvailable` | 暂停操作，稍后再查 |
| 超时或写入结果未知 | `RequestTimeout` | **先查单/对账，确认没有成功后才决定是否重试** |

## 为什么 `6003 OUTCOME_UNKNOWN` 很重要

它不代表“订单肯定失败”，而是客户端不知道服务端最终有没有处理成功。如果程序看到这个错误就
自动再下一个相同订单，可能造成重复成交。因此本项目把它映射为 `RequestTimeout`，让上层进入
查单和对账流程，而不是把它当成普通失败。

## 测试覆盖了什么

自动化测试逐项覆盖 Bifu 文档公开的 52 个业务码，并覆盖 2026-09-20 在线调用
`SANDBOX_MARKET` 实际返回的 `4006`，检查每个已知码抛出的 CCXT 异常类型和错误信息。
未知的新业务码不在适配器里猜测含义，真实 HTTP 链路测试确认后续仍由 CCXT 的 HTTP 状态处理，
且最终异常保留原始业务码和响应；等 Bifu 文档确认后再补精确映射。

## 问题与答案

1. 为什么不能把所有 HTTP 400 都当成同一种错误？  因为余额不足、参数错误和签名错误的处理
   方法完全不同，统一成一个错误会让上层做出错误重试。
2. 为什么 `NOT_ORDER_OWNER` 也映射成 `OrderNotFound`？  这样不会向当前账户透露其他账户的订单
   ID 是否真实存在。
3. 遇到 `RequestTimeout` 能不能立刻重下？  不能。先用订单 ID 或客户端订单号查询并核对账户，
   确认原操作没有成功后再决定。
4. 为什么未知业务码不自行猜测？  猜错会改变上层处理逻辑；应保留原响应并等待官方协议确认。
